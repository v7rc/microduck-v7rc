## 真實模擬器端到端測試

以下為 CH3／CH4 交換前的原始基線；原始記錄保留當時通道順序。最後完整一輪 [lan-address-run-4](evidence/2026-11-06-udp/lan-address-run-4/summary.json) 於 **13:41:58** 開始，14 個階段全部通過。驗證程式只透過 UDP 送控制；另一條只讀連線訂閱 `robot.state`，同時讀 MuJoCo 真實位置與關節資料。

| 項目 | 輸入 | 實測與判定 |
| --- | --- | --- |
| 初次回中 | 四軸 1500，3 秒 | 移動、頭部命令回中，保持直立；通過 |
| CH2 前進 | 2000，8 秒 | 平面淨位移 **0.939 m**，偏航 −32.4°；基本前進通過，精度限制仍在 |
| CH1 左轉 | 1000，6 秒 | **+287.4°**；方向與實際轉動通過 |
| CH1 右轉 | 2000，6 秒 | **−315.9°**；方向與實際轉動通過 |
| CH3 向右 | 2000，2 秒 | 頭部命令 −0.4 rad；實際 head_yaw 約 **−0.452 rad** |
| CH3 向左 | 1000，2 秒 | 頭部命令 +0.4 rad；實際 head_yaw 約 **+0.350 rad** |
| CH4 正俯仰 | 2000，2 秒 | 命令 +0.25 rad；實際 head_pitch 約 **0.682 rad**，相對中立增加約 0.227 rad |
| CH4 負俯仰 | 1000，2 秒 | 命令 −0.25 rad；實際 head_pitch 約 **0.224 rad**，相對中立減少約 0.231 rad |
| 封包中斷 | 前進後停止送包 2 秒 | 在 **0.401 秒**樣本觀察到 move.requested 歸零；末端 applied 接近 0 |
| 未回中直接重連 | 再送 CH2=2000，1 秒 | 不恢復前進；維持歸零，通過 |
| 再回中 | 四軸 1500，0.5 秒 | 重新接受輸入，後續轉向成功 |
| 錯誤封包持續到達 | 頭部負俯仰後送 CH2=9999 | 未刷新輸入；頭部平滑命令於 **0.701 秒**樣本收斂至各軸 <0.01 rad |

所有階段最低軀幹高度 **0.1129 m**、最大傾斜 **4.37°**，控制迴圈最低約 **49.84 Hz**，未觀察到 fallen。各階段也檢查回報的 requested／applied 移動與平滑頭部命令符合映射；實際頭部關節須相對實測中立姿態朝正確方向改變至少 0.1 rad。

300 ms 是橋接輸入期限；0.401 秒是每秒約 10 次的觀察樣本時間，不是精密網路延遲基準。robotd 會平滑命令，且機器人仍有動力學收斂，所以不能將 watchdog 描述成 300 ms 內實體立即停止。第一階段的速度不足、低速偶爾不起步及直線偏航均未在本次修正。

## 測試判定修正紀錄

原始各輪全部保留，沒有刪除未通過結果：

- [run-1](evidence/2026-11-06-udp/lan-address-run-1/summary.json)：首次回中只等 1 秒，未涵蓋 idle head 淡出；另以絕對關節角度判斷負俯仰，門檻不符合學習策略的中立姿態。
- [run-2](evidence/2026-11-06-udp/lan-address-run-2/summary.json)：改用實測中立姿態後，頭部正負方向通過；但把平滑後頭部回中時間與移動請求歸零時間套在同一個 0.6 秒門檻，造成判定失敗。
- [run-3](evidence/2026-11-06-udp/lan-address-run-3/summary.json)：分開檢查 move.requested 歸零（<0.6 秒）與頭部平滑收斂（<1.0 秒）後，僅首次回中等待不足仍失敗。
- [run-4](evidence/2026-11-06-udp/lan-address-run-4/summary.json)：初次回中等待 3 秒，超過上游 `idle.fade_s=1.5`；所有階段通過。這些修正針對驗證方法，沒有改動上游控制策略、致動器或 bridge 增益。

上游 `robotd-params/src/lib.rs` 與 `robotd/src/main.rs` 顯示，長時間沒人控制時會自動看向四周，收到新鮮頭部命令後以 1.5 秒淡出；`robot.state.head` 也包含平滑與 idle 偏移。因此 APP 初次回中後宜等待約 2 秒再觀察頭部中立；停止操作一段時間後，自主看向四周可能恢復。
